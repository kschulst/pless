## Original Business Requirement

> # Import documents through the Paperless REST API
>
> Without import there is no archive. This is the blocking feature.
>
> **Decided approach:** [ADR 0012](../blob/main/adr/0012-import-through-the-rest-api.md) — upload
> through `POST /api/documents/post_document/`, so duplicate detection, per-file status and
> consumption confirmation come from Paperless rather than being inferred from a folder.
>
> **Scope**
> - `pless docs upload <path>` with `--dry-run`
> - Local manifest: file → task id → outcome
> - Batching, and resume by retrying files without a successful outcome
> - Progress output; JSON output for a future web layer
> - Never deletes local files
>
> **Already done:** `pless docs scan` and `pless docs estimate` classify and size a collection.
>
> **Open question:** whether bulk first import of many gigabytes needs an rsync path as well.
> Decide after measuring, not before.

## Domain Concept Identification

### Existing Concepts (from codebase)

- **FileEntry / ScanResult** (`docscan.py`): a local file classified as ready to import, needing
  conversion, or unsupported — with an optional SHA-256. `pless docs scan` and
  `pless docs estimate` already produce these, so import does not start from nothing: it starts
  from a classification that already exists and that an operator may already have looked at.
- **Host** (`targets.Host`): the one way `pless` reaches the target. Everything — deploy, storage,
  backup, audit — goes through SSH, and `Host.tunnel_args` already exists for port forwarding.
- **`pless tunnel`**: forwards `localhost:8000` to the target's Paperless over SSH, for a browser.
  The only existing code that reaches Paperless's HTTP surface from the operator's machine.
- **`deploy.http_status`**: checks Paperless from the *target's* localhost, over SSH with `curl`.
  The only existing code that talks to the Paperless API at all, and it does so from the target.
- **`PAPERLESS_API_TOKEN`** (`config.Secrets`): already declared, already documented as created in
  the Paperless UI after deployment, and currently used by nothing.
- **`PAPERLESS_ADMIN_PASSWORD`** (`config.Secrets`): generated by `pless init --secrets` and used
  to seed the Paperless superuser. Relevant because a token can be obtained from it.
- **`[paths] local_documents`** (`config.PathsConfig`): where the operator's originals live,
  defaulting to `./documents`. The natural default for what to upload.
- **The task queue** (`backup.parse_queue_state`, and the quiescence loop in the rendered backup
  script): `pless` already has a notion of Paperless being busy, built for backup. Import is the
  thing that makes it busy.
- **One-time disclosure and `_print_verbatim`** (`cli.py`): the established patterns for secrets
  and for output the operator copies.

### New Concepts Required

- **Upload**: one local file offered to `POST /api/documents/post_document/`. Returns a task
  identifier; it is *not* a document yet.
- **Consumption task**: what Paperless does after the upload — OCR, classification, deduplication
  — reported through `/api/tasks/`. The gap between "uploaded" and "in the archive" is the whole
  reason ADR 0012 chose the API, and it is measured in minutes per document, not milliseconds.
- **Import manifest**: a durable local record of file → task → outcome. Durable because the
  outcome arrives long after the upload, which makes this the first state `pless` keeps on the
  *operator's* machine rather than on the target or in a repository.
- **Outcome**: succeeded, duplicate, failed, or still running. "Duplicate" is a *success* for the
  operator's purposes — the document is in the archive — and conflating it with failure would make
  every re-run look worse than the last.
- **Batch**: how many uploads are in flight at once. Paperless consumes serially; uploading faster
  than it consumes only grows a queue.
- **Reachability for HTTP**: a way for the operator's machine to reach an API that listens on the
  target's localhost. New, because nothing yet needs it.

### Conceptual Relationships

- A **ScanResult** names the files an **Import** will offer; one **Upload** per `FileEntry`
  classified as ready.
- An **Upload** produces a **consumption task**, and a task eventually produces an **outcome**.
  One file, one task, one outcome — but the three are separated in time, which is what the
  **manifest** exists to bridge.
- The **manifest** is the resume key. Re-running an import means offering the files whose outcome
  is not yet a success, which means the manifest must identify a file in a way that survives the
  operator moving or renaming it.
- An **Import** fills **the task queue**, and the queue is what `backup` waits to drain. Those two
  features meet here, and nothing has written down what happens when they do.

### Key Business Rules

- **Local files are never deleted or modified.** Explicit in the requirement, and the reason
  `extract` exists separately: `pless` reads the operator's originals and never owns them.
- **A duplicate is a success.** Paperless rejecting a document it already holds means the archive
  contains it. The manifest records it as done, not as an error to retry forever.
- **Outcome comes from Paperless, never inferred.** The entire argument of ADR 0012. A file that
  uploaded is not a file that was consumed, and `pless` must not report the first as the second.
- **An import is resumable and re-enterable.** Interrupting it must lose no more than the
  in-flight uploads, and running it again must neither re-upload what succeeded nor lose the
  tasks still pending.
- **Implicit rule, surfaced:** uploading must not outrun consumption. Paperless OCRs serially, so
  an unthrottled upload of ten thousand files produces a queue that takes days to drain — during
  which the operator has no way to tell progress from stall.

## Strategic Approach

### Solution Direction

A new core module for the API, a manifest on the operator's machine, and a reachability decision
that follows what `pless` already does rather than what ADR 0012 assumed.

- **`paperless.py`**, a core module in the established shape: no `typer`, no `rich`, dataclasses
  out, its own error type. It holds the API client and the pure decisions — classifying an outcome,
  deciding what to retry — behind a transport seam, as `b2.py` does.
- **An SSH tunnel for the duration of the import, not Tailscale.** ADR 0012 says the API is
  reachable "over Tailscale", which is true for a browser and assumes the operator is on the
  tailnet. But `pless` reaches the target exactly one way — SSH — and `Host.tunnel_args` already
  exists. A tunnel opened for the upload needs no new reachability assumption, works before
  `pless harden` as well as after, and keeps import working for an operator who has not joined
  the tailnet. This is the main thing to grill.
- **The manifest lives beside `pless.toml`**, as JSON, keyed by content hash. It is the first
  durable state `pless` keeps on the operator's machine, which is a new thing and deserves to be
  deliberate.
- **Upload and confirm are the same command, run twice.** `pless docs upload` offers what is not
  yet done, records the tasks, polls for as long as it is running, and leaves the rest in the
  manifest. Running it again collects outcomes that have since resolved and offers whatever still
  needs offering. That makes "resume" and "check on it" the same operation, which is one fewer
  command and one fewer concept.

### Key Design Decisions

- **Where the HTTP request comes from.** Three options: a tunnel from the operator's machine,
  Tailscale directly, or streaming each file to the target over SSH and `curl`-ing from there.
  → **A tunnel.** Tailscale adds a precondition `pless` does not otherwise need. Streaming to the
  target and posting locally would avoid the tunnel but writes every file onto the encrypted
  volume twice — once as a temporary and once as a consumed document — and turns disk pressure
  into a new failure mode. The tunnel costs an ephemeral port and a subprocess.
- **Where the API token comes from.** The token currently has to be created by hand in the
  Paperless UI, which is a manual step between deployment and import.
  → **Worth asking whether `pless` should obtain one itself**, since Paperless exposes
  `POST /api/token/` against a username and password, and `PAPERLESS_ADMIN_PASSWORD` is already in
  `.env`. That would remove a hand step from the one path every operator must take. It also means
  `pless` handling the admin password for something other than deployment, which is a decision
  rather than an obvious win.
- **What identifies a file across runs.** Path is free and breaks when the operator tidies their
  folders; content hash is stable and costs a full read of every file.
  → **Hash**, because `docscan` already computes them and because the alternative silently
  re-uploads a renamed file, which Paperless then reports as a duplicate — correct, but wasteful
  and confusing.
- **How much to have in flight.** → **Small and configurable**, defaulting to something like four.
  Paperless consumes serially, so the only thing a large batch buys is a longer queue; the only
  thing it costs is a worse interruption.
- **Whether to add an rsync bulk path.** → **Not now, and measure first**, which is what the issue
  already says and ADR 0012 already argued. The thing to measure is documents per minute over a
  domestic uplink, and whether the API or the OCR is the bottleneck. If OCR is, rsync buys
  nothing.

### Alternatives Considered

- **The consume folder:** rejected in ADR 0012. Every status question becomes guesswork about
  vanishing files, and a file that fails to parse simply stays there with no explanation.
- **A long-running import daemon on the target:** would survive the operator closing their laptop,
  and adds a service to run, keep alive and reason about. The manifest plus a re-enterable command
  gets most of the benefit with none of that.
- **Recording outcomes on the target** beside the verification record: consistent with
  [ADR 0019](../../adr/0019-the-verification-record-lives-on-the-target.md), and wrong here — the
  manifest is about *local* files, which the target knows nothing about and should not.

## Risk & Gap Analysis

### Requirement Ambiguities

- **What counts as "done" for a document that Paperless failed to parse.** A corrupt PDF will
  fail consumption forever. Retrying it every run is noise; marking it done is a lie. It needs a
  third state and a decision about whether the operator has to acknowledge it.
- **Whether `--dry-run` reports what would be uploaded, or also what Paperless would reject.** The
  first is free. The second is not possible without uploading, since duplicate detection happens
  at consumption.
- **What `pless docs upload` does about files `scan` classified as needing conversion.** Skip them
  silently, refuse to start, or report and continue? The requirement says import, and `scan`
  already names them, but nothing says which.
- **Whether the manifest is per-import or per-archive.** Importing a second folder later is the
  normal case, and one manifest keyed by hash handles it — but that makes the manifest a
  permanent artefact rather than a scratch file, and nothing says where it belongs.

### Edge Cases

- **An import that outlives the operator's session.** OCR of ten thousand documents takes days.
  The command cannot stay open that long, so the manifest must be the source of truth and
  re-running must be routine rather than exceptional.
- **A task id that Paperless no longer knows.** Paperless prunes its task list. A manifest entry
  whose task has aged out is neither succeeded nor running, and treating it as failed would
  re-upload a document that is already in the archive.
- **The operator's laptop sleeping mid-upload.** The tunnel dies and in-flight uploads are lost.
  Recoverable, provided a half-written upload cannot be recorded as sent.
- **Two imports at once**, by accident. Two processes writing one manifest corrupts it.
- **A file that is modified between runs.** Keyed by hash it is a new file and gets uploaded
  again, which is probably right and should be said out loud.
- **Paperless unreachable mid-import**, because the volume locked or the stack restarted. The
  manifest must survive it and the message must distinguish it from a file that failed.

### Technical Risks

- **This fills the queue that `backup` waits to drain.** The rendered backup script waits
  `quiescence_timeout_seconds` (default 900) for the task queue to be empty and *fails the run* if
  it is not, writing a failed record and exiting non-zero. A multi-day import therefore makes the
  nightly backup fail every night, with a record saying the export was not attempted. Nobody has
  written this interaction down, and it is the most consequential finding here: the two features
  meet and the current behaviour is wrong for the overlap.
- **The response shape of `post_document` is version-dependent.** Older Paperless returned
  `"OK"`; 2.x returns a task UUID. `[paperless] version` is pinned at 2.20.15, so this is
  checkable — but it must be checked against that version rather than assumed, which is the
  mistake the B2 work made twice.
- **Polling cost and etiquette.** `/api/tasks/` for thousands of tasks, repeatedly, against a
  Raspberry Pi. Needs batching and a sane interval, and the interval interacts with how long the
  command stays open.
- **The manifest is new state `pless` owns on the operator's machine.** Corruption, concurrent
  writes and partial writes are all now possible. The project's existing records are on the target
  and written with `tee`; this needs its own answer.
- **Nothing here can be drilled without documents.** A realistic drill needs a corpus with
  duplicates, a corrupt file, and enough volume to see throughput — which also means a drill that
  takes hours rather than minutes.

### Open questions, for grilling

In the order they change the shape of the work:

1. **How does the operator's machine reach the API?** A tunnel `pless` opens, Tailscale as
   ADR 0012 assumed, or streaming to the target and posting from there. This decides whether
   import has a precondition beyond SSH.
2. **What happens to the nightly backup during a multi-day import?** The quiescence guard fails
   the run while the queue is busy. Options include a longer timeout, a skip that is not a
   failure, or a deliberate pause — and this is a change to backup, not to import.
3. **Should `pless` obtain the API token itself** from the admin credentials it already holds,
   rather than asking the operator to create one in the UI?
4. **What is the third state** for a document Paperless will never successfully consume, and does
   the operator have to acknowledge it?
5. **Where does the manifest live, and is it permanent?** It is the first durable state `pless`
   keeps on the operator's machine.
6. **What does `upload` do with files `scan` classified as needing conversion?**
